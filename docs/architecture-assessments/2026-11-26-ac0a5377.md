Assessment date: 26 November 2026.

Assessed commit: [ac0a5377b9e92096fd4917290da80ccad70db2ec](https://github.com/chepetime/factory-elections/commit/ac0a5377b9e92096fd4917290da80ccad70db2ec) (main at review time).

This assessment is a historical snapshot. Its findings apply to that commit. Keep later assessments in new dated files. The [current architecture](https://github.com/chepetime/factory-elections/blob/main/docs/architecture.md) is maintained separately.

## Decision

Keep the local modular monolith. Consolidate execution ownership and durable operations before adding more autonomous workflows or general project types. Preserve the domain core, adapter ports, exact-commit gates, and evidence records.

The architecture fits a local software factory. Its strongest property is controlled change: a model produces work, deterministic checks assess it, and a person approves a specific commit. Its main weakness is that execution policy spans several service lifecycles. More features increase the number of places that must agree about cancellation, recovery, capacity, and cost.

This is a source assessment, not a production reliability certificate. It covers the core, driver, backend composition and recovery, storage adapter, provider selection, feature orchestration, and Docs integration. Existing tests supply evidence of intended behavior. No paid provider run, GitHub publication, load test, or crash experiment forms part of this review.

## Goals and current scope

The README defines the current promise: turn a repository task into a verified, reviewed change, then stop for human approval before publication. The product vision extends this to feature planning, parallel implementation, PR tending, shared attention management, and eventually non-code work.

These are different maturity levels. Repository execution is the foundation. General project types and a tool broker are target designs. Their presence in the vision does not prove that the current app implements them.

## What is architecturally sound

### Approval binds to evidence

The driver checks commit identity at review, approval, and publication. Verification detects a moving HEAD. Revision clears approval before new work. This prevents an old approval from authorizing a new change. Preserve these rules during every runtime refactor.

Evidence receipts and configuration manifests strengthen this design. A local signature proves origin and integrity within the installation. It does not prove that a model review is correct or that the installation is independently trusted.

### Execution is distinct from task progress

Core execution types separate outcome, cleanup, and provider-session identity. A task stage alone does not prove that a process is live. The backend tracks ownership through finalization. This supports accurate controls and safe recovery.

### Provider substitution does not erase safety differences

The shared runner checks capabilities. Composition selects the Codex batch or app-server transport. Claude remains a separate implementation. This is better than pretending that all providers support identical guards, costs, and cancellation.

### Storage has explicit failure boundaries

The data adapter uses transactions and advisory locks. Artifact writes use bounded buffering and integrity checks. Configured storage does not silently fall back to stale files. These choices protect the authoritative record and expose failure instead of hiding it.

### Existing tests target meaningful invariants

Backend server tests cover duplicate starts, shutdown, restart, parallel execution, finalization failure, invalid execution metadata, cancellation, and uncertain cleanup. These are valuable architectural tests. Keep them as acceptance tests for structural changes.

## What needs to change

### 1. Finish one execution lifecycle — highest priority

Evidence: task scheduling and recovery live in the backend service; feature steps have their own background lifecycle; reviews support SDK and CLI paths; agent pickup has its own timer and retry state. Shared slots already exist. Shared slots alone do not establish one recovery and cancellation contract.

Introduce a backend execution manager with explicit submit, observe, interrupt, reconcile, and finalize operations. Each workflow owns its domain transitions. The manager owns capacity, attempt identity, provider sessions, cleanup, usage, and evidence closure. Adapt one caller at a time. Do not replace the software driver with a generic workflow engine.

Acceptance: the same lifecycle suite passes for tasks, reviews, chats, feature steps, and children. Restart cannot create two owners. Cancellation reports cleanup independently from outcome. No capacity reservation leaks after a failed start or failed finalization.

### 2. Make recovery failures visible — highest priority

Evidence: `BackendService.recover` converts a failed task listing into an empty list and a failed latest-run read into an absent run. This can skip reconciliation without explaining the missing work. This is a source-level risk, not an observed incident.

Record a recovery report per project. Distinguish missing records from unreadable or invalid records. Expose degraded recovery through health and the inbox. Refuse affected mutations when ownership cannot be established.

Acceptance: an injected list/read failure produces a visible degraded state. A later successful reconciliation clears it without duplicate execution.

### 3. Record external action intent and reconciliation — high priority

Evidence: publication pushes, queries GitHub for an existing PR, creates if needed, then persists the result. The existing lookup reduces duplicate creation. GitHub and local storage still cannot commit together.

Persist publication intent with the approved commit and a stable operation ID. Record the external result. After an ambiguous failure, reconcile the branch and PR before allowing another creation attempt. Apply this pattern to future external writes from tending and tools.

Acceptance: inject a crash after each external action and before its local save. Recovery finds the existing result or asks for a decision. It never silently repeats an ambiguous write.

### 4. Document and test the complete storage boundary — high priority

Evidence: tasks and artifacts use configured storage, while profiles and feature files also use filesystem paths. PG/S3 is therefore not the whole installation state.

Publish an ownership table for every durable entity. State its authoritative store, schema version, lock, backup method, and restore order. Add a full-installation restore test. Add reconciliation for orphan artifact objects. Keep file-backed entities where they suit local use; migrate only when transactional relationships require it.

Acceptance: restore projects, profiles, tasks, feature plans, evidence, and receipt keys into a clean installation. Verify links and signatures. No record silently refers to missing authoritative data.

### 5. Reduce policy concentration — medium priority

Evidence: the baseline driver workflow has 1,639 lines; the backend service has 1,445. Size alone is not a defect. Their mix of orchestration, recovery, gates, and evidence makes invariant changes harder to review.

Extract coherent internal modules: verification, publication, run ownership, and reconciliation. Keep small command interfaces. Move pure decisions to core only when they have no process or storage dependency. Avoid creating a service or package for every helper.

Acceptance: transport handlers cannot bypass gates. Existing behavioral tests remain valid. Dependency checks prevent core from importing backend or adapters.

### 6. Reconcile the roadmap with source — medium priority

The roadmap still describes shared execution identity and cleanup separation as phase work. Core already defines these concepts. Composition already exposes the Codex app-server flag. Local backend prose also contains older concurrency language. The state-machine document says “Known gaps: None,” which should not be read as a system-wide assurance.

Give each roadmap capability a status: implemented, partially integrated, experimentally verified, or planned. Link each status to source and a test. Keep transport-specific limitations visible.

## Recommended direction

### First: establish a reliable local execution platform

Complete lifecycle parity, visible recovery, and external-action reconciliation. Keep one backend and one host owner. Add metrics for queue wait, interrupted work, uncertain cleanup, finalization failures, unknown cost, and human attention time. Measure results before adding more automatic behavior.

Exit: crash and cancellation scenarios pass across execution types. Every accepted execution has a durable identity, a terminal result or explicit interruption, and a visible cleanup state.

### Next: deepen the software workflow

Make feature planning, ticket execution, QA, and tending use the same execution contract. Keep their business rules separate. Prioritize complete feature-to-PR journeys over more agent roles. Add scoped tool grants before broadening external write access.

Exit: a feature can progress through planning and implementation with clear human gates. Every external write has an actor, scope, intent, and recorded result. Measure completion rate, intervention time, and verified-change cost.

### Then: generalize the product model

Separate project identity from repository resources. Keep software stages inside the software workflow. Introduce non-code artifacts and conversations only after their ownership and provenance rules are explicit. Start with one non-code journey from the vision, such as preparing a 1:1.

Exit: that journey works without a fake repository or software-only task stages. Existing repository approval rules remain intact.

### Defer distributed infrastructure

The current product is local and single-owner. Microservices, a remote worker fleet, or a new workflow platform add coordination costs before a measured need exists. Reconsider them when remote execution, multi-user tenancy, or sustained queue pressure becomes a product requirement. Durable ownership and reconciliation remain prerequisites.
