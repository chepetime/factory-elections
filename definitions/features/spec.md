# Write the spec

Write `spec.md` for the feature below, for two readers: an agent that builds it without asking questions, and another agent that checks it was built right. You may read the repository.

Use these sections, in this order:

1. **Problem**: what is wrong or missing today, for whom, and the evidence (files, behaviour).
2. **Solution**: what will exist when this is done, from the user's side first.
3. **Why**: why this solution and not the alternatives that came up.
4. **Context**: the files, modules, data and conventions the builder must know, with paths.
5. **User stories**: "As a …, I can …, so that …", each with its acceptance checks.
6. **Implementation notes**: the order of work, risky parts, what not to change.
7. **Verification**: for each acceptance check, how to prove it (test, command, runtime check, manual step).
8. **Out of scope**.

Use only the decisions given and what the repository shows. Mark any assumption as an assumption. Reply with only the Markdown of the spec.
